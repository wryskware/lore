# Ingestion

How content reaches the index. Decided by D-0015 (with project identity from
D-0016); the proposal history and rejected alternatives live in
[[2026-08-16_ingestion-inversion-decision-brief]].

## Topology

> [!accepted] D-0015
> Ingestion is push. One filesystem observer per machine. The index owner
> never reads a filesystem it does not own.

```text
            ┌────────────────── one machine ──────────────────┐
            │  agents (MCP / CLI: search, expand, status)     │
            │        │  read-only verbs, loopback (D-0007)    │
            │        ▼                                        │
            │  ┌──────────────── local daemon ─────────────┐  │
            │  │ walker + watcher (sole filesystem observer)│  │
            │  │        │ snapshot (in-process,             │  │
            │  │        ▼  lore-core wire types)            │  │
            │  │ ingest pipeline → store (local index)      │  │
            │  └────────┬───────────────────────────────────┘  │
            └───────────┼──────────────────────────────────────┘
                        │ optional remote hop: the same snapshot,
                        │ serialized (push protocol, TLS)
                        ▼
              ┌─ remote daemon (self-hosted box, etc.) ─┐
              │ push routes → staging → commit → store  │
              │ search/expand served from its own index │
              └─────────────────────────────────────────┘
```

Two deployment modes, one pipeline:

- **Local (default).** The walker feeds the snapshot interface in-process.
  Disk remains the content source; `expand` reads files directly; nothing is
  retained beyond today's store. User-visible behavior is unchanged.
- **Remote.** The local daemon doubles as a *forwarder*: it observes the
  filesystem and pushes snapshots to a remote daemon that owns the index —
  a headless home server is the canonical example. The push routes ship in
  the public daemon, loopback-only by default; exposing them further is a
  deployment's own responsibility (see Trust boundary).

Agent clients never push and never trigger walks — they do not have the
verbs, so independent agents cannot race to reindex (D-0003's single-owner
principle).

## The snapshot contract

A push is a **manifest**: the complete listing of a project's ignore-filtered
files as `(path, content-hash, size)`.

- **Full listing, always.** ~100 bytes/file; a 300k-file repo is a ~30MB
  compressible listing. A checksummed delta encoding against a daemon-named
  base generation is a permitted *wire optimization* later; the semantic
  unit stays the full manifest, verified by a full-manifest checksum.
- **Deletion is omission.** There is no delete event to lose, reorder, or
  replay.
- **Mass-delete guard.** A push that would delete more than **50% and more
  than 100 files** of a project is rejected unless the invocation carries an
  explicit CLI override flag. The override is per-invocation, never a config
  key. A tripped guard is visible in `status`.

### Refused by name

> [!accepted] D-0015
> No incremental mutation protocol — no client-streamed "file changed / file
> deleted" events, ever. That is where the concurrency bugs live. Proposals
> to add one "for performance" reopen that door; the manifest negotiation
> must stay fast enough that nobody wants to.

> [!accepted] D-0015
> No content-addressed blob store with multi-generation retention and
> reference-counted GC. The store keeps **current generation only**, keyed
> `(project, path)` — replaced on write, removed on omission, inside the
> commit transaction. The only cleanup is deleting a push session's staging
> directory on commit or lease expiry.

## Push flow

1. **Lease.** The pusher acquires the project's push lease (see below) and a
   session handle.
2. **Manifest.** Pusher sends the manifest; the daemon diffs it against
   committed state and answers with the paths whose content it needs
   (hashes matching committed *or* already-staged content are skipped —
   file-level resumption falls out for free).
3. **Upload.** Needed files land in a per-push staging area keyed by
   session. A dead session leaves inert staged files; the index never sees
   partial state.
4. **Commit.** One transaction: upsert changed files, delete omitted ones,
   advance the project generation. Searches see the old generation until the
   flip. This is the existing index-pass apply/prune with a different
   observation source; chunking and `CHUNK_FORMAT_VERSION` stay daemon-side —
   clients send content, never chunks.

## Leases and epochs

- Per-project push lease with a **monotonically increasing epoch**; every
  push names its epoch. Heartbeat + TTL, so a dead pusher blocks a successor
  for seconds, not until cleanup.
- Conflict policy is **takeover**: a second acquirer bumps the epoch; the
  stale pusher's next push is rejected with a named error. Sustained
  contention degrades to flapping between internally-consistent snapshots —
  detectable as epoch churn in `status`, never interleaved state.
- Session handles are unguessable and bound to project + epoch; the commit
  verifies the epoch in the same transaction that publishes the generation.
- A lease is a consistency primitive, **not** an authorization grant.

## Cadence

Watcher debounce batches changes into micro-manifests at **~20–30s**
(config key; exact default is an implementation constant). Bench round 1
showed agent retrieval is front-loaded at task start — searching for code
*while* editing it is pathological, so sub-10s freshness buys nothing.
`lore index` remains the immediate path. A receiving daemon enforces a
**hard minimum push interval** and rejects clients configured hotter.

## Ignore rules and secrets

> [!accepted] D-0020
> One ignore evaluation, pusher-side, with `.loreignore` sovereign. The
> receiver validates structure, never content.

- Exactly **one evaluator** decides what is observed, with rule sources
  stacked lowest to highest: an **optional user-level loreignore** (at
  `<data-dir>/loreignore`, undotted beside `config.toml`, scoped by
  `LORE_DATA_DIR`; installed only by explicit choice — a commented template
  of dot-file, credential, and ecosystem patterns ships as the
  `lore setup ignore` asset; absent = empty source) → the repo's own
  **`.gitignore`**, honored as a courtesy through the same evaluator (no
  git subprocess, no tracked/untracked distinction, no global gitignore,
  no `core.excludesFile`; repo declarations outrank user defaults) → the
  project's **`.loreignore`**, sovereign — it inherits the lower sources
  and its re-includes beat everything below. The binary compiles in **no
  ignore opinions**: out of the box lore observes everything except the
  `.git/` floor and the daemon's own data dir, dotfiles included — chosen,
  not accidental. Untracked files are observed like any other. No entropy
  scanning (killed: false-positive-prone, trains reflex-overrides).
- Re-including a credential file is an ordinary `!` line in a committed
  `.loreignore` — visible in review, and deliberately the user's call. The
  accepted trade (D-0020): a bad ignore file can admit a secret; hygiene
  here is best-effort user responsibility, and encrypted stores are the
  substantive data-protection measure.
- The **receiving daemon validates structure only**: malformed paths
  (traversal-shaped, absolute, empty) reject the manifest as broken-client,
  and `.git/` components are refused as lore's own metadata floor. What a
  manifest may otherwise contain is the pusher's business (trusted-client
  model; in shared deployments, isolation comes from the instance boundary,
  not content policy).
- There is no `.loreignore` generation and no `lore init`: gitignore
  courtesy plus the optionally installed user-level file cover the common
  cases, and a project `.loreignore` exists only where a human wrote one.
  `lore add` writes only `.lore.toml`; `lore setup` is the explicit
  install surface for optional assets, the user-level template included.

## Project extent: where the project stops

Distinct from the ignore stack above, and deliberately so. The rules decide
what is *interesting*; these decide *whose content this is* — a question no
ignore file asks. Both boundaries are descent decisions, not a fourth rule
source, and they differ in one telling way: one is overridable and one is not.

> [!accepted] D-0021
> Symbolic links do not implicitly extend a project. Filesystem topology does
> not define project topology.

- **A nested repository root** is not descended into: everything under it is
  another repository's content, most concretely an agent tool's `git worktree`
  of this very project, which is a byte-for-byte second copy chunked twice.
  This boundary **is** overridable — `!vendor/dep/` in the project's own
  `.loreignore` rescues a deliberately vendored repository.
- **A link is not followed**, in any direction, with **no override**. To a
  directory: not descended. To a file: the target is not indexed through the
  link either, which would put one content at two logical paths in a store
  keyed `(project, path)`. Escaping the root: emphatically not, so that no link
  can turn a project into an index of `~/secrets` or a company mount. A
  Windows junction is a link throughout — the platform reports one as the
  other.
- **The one asymmetry is deliberate.** A `!` on a vendored repository answers
  "whose content is this", and the owner may answer "mine". A `!` on a link
  would instead **extend the project's extent to another part of the
  filesystem**. Same syntax, different act; they do not share a mechanism.
- **The project root may itself be a link.** It is canonicalized at
  registration, and the physical root is what is walked, watched and used for
  containment.
- **Creating, deleting or retargeting a link** is an ordinary filesystem event,
  processed so that stale indexed state reconciles. The new target is not
  traversed.
- **Declined links are reported**, never silently dropped: a walk names them, a
  pass counts them (`links_skipped`) and warns with the paths. The defect this
  closes was never a wrong index — it was a project whose whole corpus sat
  behind junctions reporting `files: 3` and nothing else.
- There is **no `follow_symlinks` option** and no `.lore.toml` traversal key.
  If external content is ever genuinely wanted the direction to reach for is an
  explicit additional source root with a declared mount — recorded in
  [[2026-08-17_link-traversal-decision-brief]] as direction, not design.

The incremental path reaches the same verdict as the full scan, which is the
property the whole snapshot seam exists for: `observe_paths` confirms every
watcher-named file by listing its parent through the same root-rooted walker,
so a path behind a link is absent from the micro-manifest and — being in scope
— deleted rather than left as an orphan.

## Storage

- **Local:** unchanged. Disk is the content source; `expand` reads files.
- **Remote:** the store retains **compressed current-generation file text**
  of the ignore-filtered subset, to serve `expand` context server-side. The
  chunk store already retains text for FTS5/excerpts, so this is a bounded
  multiple of existing storage, not a new category.
- **Encrypted stores:** the store must be able to open with an **externally
  supplied key held only in memory and never persisted** by the daemon.
  Locally that is a privacy feature (tracked in the backlog); how a key
  reaches a remote daemon is a deployment concern outside the core.

## Trust boundary

The daemon remains a trusted-local service: loopback-only by default, no
users, no roles, no authorization concepts. Every data operation is scoped
to one resolved project (D-0016: registry-bound declared names; duplicates
rejected at `lore add`; containment is discovery convenience, never
identity, and a declared name is never proof of access). Deployments that
serve more than one trusting party must authenticate and authorize callers
*in front of* the daemon — issue #18's scope. Nothing here makes the daemon
safe for direct Internet exposure.
