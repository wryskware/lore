# Brief C — Local Code-Embedding Calibration

**As of 2026-08-14.** Scope: open weights only, local inference on an RTX 5090 (32 GB), Windows 11, and code retrieval rather than generic sentence similarity. VRAM figures below are engineering estimates: weight storage is approximately 2 bytes/parameter at FP16/BF16 and 1 byte/parameter at INT8; runtime memory is higher because of activations, tokenizer buffers, batching, and context.

## 2. What can be said about C#

Jina Code is the clearest positive: C# is explicitly in its supported programming-language set and in the 15-language retrieval suite. CodeSage is the next-best evidence because “c-sharp” is explicitly among its nine training languages, although its public evaluation table does not isolate C#. Qwen3 has broad programming-language coverage, but its public score tables do not provide C# slices. Nomic, NV-EmbedCode, and CodeSearchNet-based comparisons are visibly Python-heavy or limited to other languages. Consequently, a C#-heavy engine evaluation should use a local C# set—especially .NET APIs, generics, attributes, LINQ, async/await, and framework names—rather than borrowing a Python-heavy CoIR/MTEB score.

## 3. Quality gap over tiny CPU defaults

The usual zero-config defaults are generic sentence models: `all-MiniLM-L6-v2` is 22.7M parameters, 384 dimensions, and truncates beyond 256 word pieces; `bge-small-en-v1.5` is 33.4M, 384 dimensions, and 512 tokens. Their public cards report generic MTEB retrieval, not code-specific CoIR performance. They are excellent installation baselines, but they were not trained as code retrievers. [MiniLM card](https://huggingface.co/sentence-transformers/all-MiniLM-L6-v2), [BGE card](https://huggingface.co/BAAI/bge-small-en-v1.5)

There is no clean, widely reported, same-protocol MiniLM-vs-Qwen/Jina CoIR table to support a precise multiplier. The defensible calibration is:

* A code-trained 130–400M model can already beat a generic tiny model by a large margin on code, so parameter count alone is not the explanation.
* Within CodeSage v2, moving 130M → 1.3B raises the released NL2Code average from 64.41 to 69.38 (+5.0 points) and code-to-code average from 38.13 to 51.55 (+13.4 points).
* Within Nomic’s own CodeSearchNet table, 137M CodeRankEmbed → 7B Nomic rises from roughly 77.9 to 81.2 (+3.3 points), while the 1.3B CodeSage v2 comparison is roughly 74.3. This is a vendor-controlled comparison and only six languages.
* Jina Code 0.5B’s 78.41 overall average versus Qwen3-Embedding-0.6B’s 73.49 is a roughly five-point gap at nearly the same size; specialization and training recipe matter as much as scale.

So the practical expectation over a generic 100M ONNX default is **roughly a 5–15 nDCG/recall-point headroom on code retrieval**, sometimes more on semantic or cross-language queries, but not a guaranteed universal multiplier. A reranker, chunking policy, symbol metadata, and hybrid lexical search can erase or exceed the embedding-model difference on easy queries. Measure on the target repository.

**Recommended default stack:** native `llama-server` with its CUDA build, an official GGUF, `--embedding --pooling last`, large token batches, and the `/v1/embeddings` endpoint. Start with **Jina Code 1.5B** for code/C# retrieval and **Qwen3-Embedding-4B** for mixed code-plus-prose; run Qwen3-8B as the quality ceiling. Keep the model’s query/document instruction prefixes, EOS handling, pooling, and normalization exactly as its card specifies. This avoids a WSL requirement while still exercising the models that matter.

## 5. Latency and batching reality check

One million lines of code is commonly about **8–20M model tokens**, depending on language, comments, generated code, and tokenizer. With 256–512-token symbol-aware chunks, a 5090 should plausibly process a small 0.5–1.5B model at **tens to low hundreds of thousands of tokens/second** when heavily batched, and 4–8B models at roughly **10–80K tokens/second**. These are planning bands, not promised benchmarks; batch size, sequence-length variance, quantization, and server implementation dominate.

That implies approximately **1–10 minutes of model time** for the small specialist and **3–25 minutes** for a 4–8B model over 1M LOC. Tokenization, parsing, disk I/O, vector serialization, and ANN-index construction usually make the end-to-end job more like **5–30 minutes**. Batch size 1 can be an order of magnitude slower than a token-budgeted batch. For interactive queries, keep a separate low-concurrency path or a second small model; indexing throughput and single-query latency are different operating points.

## Implications for engine evaluation

An engine is only able to benefit from this quality headroom if its embedding provider is replaceable. At minimum it needs a configurable **base URL** (including `/v1` path handling), model ID, authentication/header passthrough, batch input, timeout/retry/backpressure controls, and compatibility with OpenAI-shaped responses. It should not assume that embeddings are 384-dimensional: Qwen3, Jina, Nomic, and CodeSage span 896–4096 dimensions and several support Matryoshka truncation. Dimension should be discovered or configured before index creation, and the vector store schema must be rebuilt when it changes.

Model identity must include revision, tokenizer, pooling, normalization, instruction/prefix mode, and output dimension—not just a friendly model name. Query and document encoding may intentionally differ (`nl2code_query` vs `nl2code_document`, or Qwen/Nomic instructions), so a provider API that only accepts one opaque string is insufficient for fair evaluation. Finally, changing any of those parameters must trigger a deliberate re-index or maintain versioned indexes; silently mixing vectors from two models makes recall measurements meaningless. A strong candidate engine therefore needs custom-endpoint support, dimension-flexible storage, model fingerprints, and an explicit re-index-on-change workflow. Without those, the RTX 5090 and the open models above are largely unreachable from the evaluation harness.
